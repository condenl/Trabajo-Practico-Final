## [cite_start]C. Forma de trabajo [cite: 54]
[cite_start]Es preciso destacar que de acuerdo a la filosofía del Proceso Unificado (y de todo proceso iterativo e incremental), todos los artefactos son objeto de modificaciones a lo largo del proceso de desarrollo, con lo cual, sólo al término del proceso podríamos tener una versión definitiva y completa de cada uno de ellos. [cite: 55] [cite_start]Sin embargo, el resultado de cada iteración y los hitos del proyecto están enfocados a conseguir un cierto grado de completitud y estabilidad de los artefactos. [cite: 56]

[cite_start]Tanto TC como TD se presentan como materias complementarias ya que para completar el total del sistema es necesario realizar las actividades requeridas en ambas asignaturas. [cite: 57] [cite_start]En ambas asignaturas se presentan un conjunto de artefactos entregables y funcionalidades requeridas que serán realizadas durante la cursada. [cite: 58] [cite_start]Utilizando el concepto de procesos unificado de desarrollo y diferentes conceptos de desarrollo ágil de software. [cite: 59] [cite_start]Se espera que los diferentes ítems solicitados sean realizados durante 3 iteraciones a lo largo del cuatrimestre, las cuales tienen un alcance detallado y definido de cada uno de estos ítems. [cite: 60]

[cite_start]El total de los ítems están separados en 5 grandes grupos, a saber: [cite: 61]
* G00. [cite_start]Descripción global del producto. [cite: 62]
* N00. [cite_start]Procesos de negocio. [cite: 63]
* T00. [cite_start]Documentos de aspectos técnicos que provee el sistema de información. [cite: 64]
* A00. Características y funcionalidades adicionales. D00. [cite_start]Documentación adicional. [cite: 65]

[cite_start]En cada uno de los grupos, se utilizarán técnicas basadas en una versión reducida del proceso unificado de desarrollo, el cual está dividido en fase y flujos de trabajo (actividades). [cite: 66] [cite_start]De esta manera, se harán 3 iteraciones en las cuales se utilizaran para completar todos los ítems del proyecto, poniendo énfasis en las diferentes actividades según lo solicitado en el plan de trabajo de la asignatura. [cite: 67] [cite_start]La aprobación de la cursada está sujeta a la aprobación de cada una de las iteraciones, las cuales están reflejadas en 3 entregas formales que deberán cumplirse de forma obligatoria. [cite: 68]

### G07. [cite_start]Modelo de datos parcial de todos los módulos implementados [cite: 133]
Integración de todos los modelos de datos parciales de cada módulo. [cite_start]Deberán separarse los aspectos técnicos y el negocio. [cite: 134] [cite_start]Previendo que la persistencia de la información del sistema será soportada por una base de datos relacional, este modelo describe la representación lógica de los datos persistentes, de acuerdo con el enfoque para el modelado relacional de datos. [cite: 135] [cite_start]Para expresar este modelo se utiliza un Diagrama de Entidad Relación (DER). [cite: 136]

[cite_start]El modelo de datos debe dar respuesta a preguntas específicas que son importantes para cualquier aplicación de procesamiento de datos. [cite: 137] [cite_start]Para poder dar esas respuestas el modelado de datos utiliza el diagrama entidad-relación (DER), el cual permite identificar objetos de datos (entidades) y las relaciones que las unen, mediante una notación gráfica. [cite: 138] [cite_start]La representación del modelo de datos se compone de tres partes relacionadas: las entidades, los atributos que las describen y las relaciones que las conecta entre sí. [cite: 139] [cite_start]Los siguientes elementos más la 1,2 y 3 forma normal deberán estar presentes en un DER. [cite: 140]

* [cite_start]Una entidad es una representación de un conjunto de atributos que definen a un objeto de datos. [cite: 141]
* [cite_start]Un atributo es una característica cualitativa o cuantitativa que describe a la entidad. [cite: 142]
* [cite_start]Las relaciones que permiten relacionar distintas entidades a partir de sus atributos claves. [cite: 143] [cite_start]Para poder clarificar que son las relaciones debemos introducir dos conceptos: la cardinalidad y la modalidad. [cite: 144]
  * [cite_start]La cardinalidad indica para una tupla de una entidad con cuantas tuplas, como máximo, de otra entidad se relaciona. [cite: 145] [cite_start]Su valor mínimo es 1 "uno " y su valor máximo * "muchos". [cite: 146]
  * [cite_start]La modalidad indica para una tupla de una entidad con cuantas tuplas, como mínimo, de otra entidad se relaciona. [cite: 147] [cite_start]Su valor mínimo es 0 "cero" y su valor máximo 1 "uno". [cite: 148]
* [cite_start]La semántica expresa el significado o sentido de la relación. [cite: 150]

[cite_start]Simbología a utilizar para el DER: [cite: 151]

| Representación | Modalidad | Cardinalidad | Ocurrencia |
| :--- | :--- | :--- | :--- |
| + | Cero | Una | Ninguna o una |
| Una | Una | Una | Una y solo Una |
| Cero | Muchas | Muchas | Ninguna o muchas |
| Una | Muchas | Muchas | Una o muchas |

## [cite_start]C. Especificación de Casos de Prueba [cite: 402, 403]
[cite_start]Cada prueba es especificada mediante un documento que establece las condiciones de ejecución, las entradas de la prueba, y los resultados esperados. [cite: 404] [cite_start]Estos casos de prueba son aplicados como pruebas de regresión en cada iteración. [cite: 405] [cite_start]Cada caso de prueba llevará asociado un procedimiento de prueba con las instrucciones para realizar la prueba, y dependiendo del tipo de prueba dicho procedimiento podrá ser automatizable mediante un script de prueba. [cite: 406]

### i. [cite_start]Pruebas Unitarias [cite: 407, 408]
[cite_start]En desarrollo del software, una prueba unitaria es una forma de probar la corrección de un módulo de código. [cite: 409] [cite_start]La idea es escribir casos de prueba para cada función no trivial o método en el módulo de forma que cada caso sea independiente del resto. [cite: 410] [cite_start]Para que una prueba unitaria sea buena se deben cumplir los siguientes requisitos: [cite: 411]
* **Automatizable:** no debería requerirse una intervención manual. Esto es especialmente útil para la integración continua. [cite: 412]
* [cite_start]**Completas:** deben cubrir la mayor cantidad de código. [cite: 413]
* [cite_start]**Repetibles:** no se deben crear pruebas que sólo puedan ser ejecutadas una sola vez. [cite: 414] [cite_start]También es útil para la integración continua y para las pruebas de regresión. [cite: 415]
* [cite_start]**Independientes:** la ejecución de una prueba no debe afectar a la ejecución de otra. [cite: 416]
* **Profesionales:** las pruebas deben ser consideradas igual que el código, con la misma profesionalidad, documentación, etc. [cite: 417]
